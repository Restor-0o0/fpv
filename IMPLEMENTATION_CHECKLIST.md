# FPV Drones - чеклист качественной реализации

Документ составлен по `FPV_IDEAS.md`, `ARCHITECTURE.md`,
`rc_transmitter_spec.md` и текущему состоянию кода. Это рабочий порядок разработки,
а не список пожеланий: пункт считается завершенным только после выполнения его
критериев приемки.

## Обозначения

- `[x]` - основа уже есть в коде;
- `[ ]` - требуется реализовать или довести до рабочего состояния;
- `P0` - блокер корректности, сохранности мира или multiplayer;
- `P1` - основная игровая фича;
- `P2` - расширение после готового основного цикла;
- `DoD` - критерии, по которым фича действительно готова.

Галочка у существующего каркаса не означает, что вся подсистема завершена.

## Рекомендуемый порядок

1. Исправить P0-блокеры данных, физики, боя и серверной авторитетности.
2. Довести ручные гонки и ворота до уровня FPV-симулятора.
3. Стабилизировать ghost-систему и leaderboard.
4. Сделать data-driven модель трассы и только затем worldgen трасс.
5. Довести модульную сборку, батарею и survival-цикл.
6. Доработать NPC, payload и companion-механику.
7. Добавить радио, failsafe и антидрон-контригру.
8. После стабильной телеметрии сделать полноценный replay.

**DoD**

- Дрон на высокой скорости не проскакивает ворота между тиками.

- Reload, удаление ворот и disconnect дают предсказуемый DNF/abort без мусора в
  памяти и HUD.

## 4. Генерация качественных трасс в мире

**Статус:** отсутствует. В проекте нет worldgen structures, template pools,
track profiles или terrain validator.

Генератор нельзя делать простым случайным размещением ворот. Сначала он должен
доказать геометрическую и динамическую проходимость маршрута, и только потом
транзакционно изменить мир.

### 4.1. Data-driven контракт

- [ ] Использовать `TrackDefinition` из ручных трасс как единый runtime-формат.
- [ ] Добавить JSON/Codec-профили в
  `data/<namespace>/fpv/track_profiles/<id>.json`.
- [ ] Описывать vehicle class, длину, число ворот, AGL, clearance, curvature,
  climb angle, биомы, сложность, декор и validation profile.
- [ ] Версионировать generator algorithm; одинаковые seed/profile/version должны
  давать одинаковый результат.
- [ ] Добавить biome/structure/block tags для allowed, avoid, replaceable и
  protected областей.

### 4.2. Выбор местности

- [ ] Детерминированно выбирать несколько candidate regions, а не первый
  случайный чанк.
- [ ] Оценивать площадь, slope, roughness, воду, лаву, кроны, навесы, пещеры,
  чужие структуры, world border и расстояние до других трасс.
- [ ] Находить ровную pit/start area с безопасным launch corridor и пешим
  доступом игрока.
- [ ] Не force-load произвольных чанков из worldgen thread; использовать
  reservation и deferred placement после готовности нужных chunks.
- [ ] Сохранять причину отклонения candidate и seed для настройки генератора.

### 4.3. Построение маршрута

- [ ] Строить terrain-aware centerline через beam search/RRT* или эквивалентный
  ограниченный поиск в 3D.
- [ ] Проверять swept corridor для целевого класса дрона на каждом segment.
- [ ] Ограничить curvature, climb/dive, минимальную длину segment и расстояние от
  ранее пройденных частей.
- [ ] Поощрять разнообразие высот и поворотов, штрафовать пустые прямые,
  хаотичный zigzag и слепые ворота за препятствием.
- [ ] Для loop отдельно строить последние 20-30% к start с согласованным tangent,
  а не соединять маршрут резким последним segment.
- [ ] Сглаживать spline и повторно валидировать corridor после сглаживания.
- [ ] Ставить ворота по arc length и в интересных точках; normal брать из tangent.

### 4.4. Доказательство проходимости

- [ ] Геометрически проверить весь swept capsule/ellipsoid и каждый aperture.
- [ ] Выполнить 3D A* по свободному пространству через ordered gates.
- [ ] Запустить детерминированного validation pilot с реальными thrust, drag,
  max rate, массой и braking distance целевого класса.
- [ ] Выполнить несколько прогонов с perturbations позиции, скорости и
  пропущенным input tick.
- [ ] Отклонять трассу при низком success rate; не чинить ее небезопасным
  принудительным соединением.
- [ ] Рассчитать и сохранить difficulty score.

### 4.5. Размещение и эксплуатация

- [ ] Сначала собрать полный placement plan, затем повторно проверить snapshot.
- [ ] Размещать start, supports, gates и декор транзакционно с rollback только
  измененных генератором блоков.
- [ ] Переживать server crash/restart без половины трассы в мире.
- [ ] Использовать structure templates для pit, supports, tunnel, spectator и
  finish, но не связывать core geometry с одним набором декора.
- [ ] Добавить команды `/fpv track validate`, `generate`, `explain`, `remove`.
- [ ] Ограничить время генерации, число обследованных chunks и blocks changed.
- [ ] Добавить seed-batch тесты по всем поддержанным биомам и измерять причины
  отказов.

### 4.6. Будущие аддоны для structure mods

- [ ] Сначала реализовать безопасный режим avoidance через data tags.
- [ ] Определить marker contract: start anchor, gate anchor, corridor entry/exit,
  no-obstacle volume и spectator anchor.
- [ ] Дать аддонам добавлять templates, pools, processors и profiles datapack-ом
  без изменения core Java.
- [ ] Для интеграции внутрь существующей структуры требовать явные entry/exit,
  bounds и свободный corridor; не проводить трассу через случайный bounding box.
- [ ] Вынести optional Java-интеграции в `compat` adapters без hard dependency.
- [ ] Ошибка или отсутствие стороннего мода не должны ломать загрузку core.
- [ ] Проверить минимум два разных structure pack отдельными compatibility
  datapacks/addons.

**DoD**

- На фиксированном наборе seed нет ворот внутри блоков, висящих опор,
  недоступного старта и непроходимых segments.
- Трассы выглядят намеренно спроектированными: читаемый flow, разнообразие без
  случайного zigzag, безопасная линия к следующему gate.
- Генерация имеет жесткий budget и не вызывает chunk cascade или заметных
  зависаний сервера.
- Datapack может добавить новый профиль и визуальный набор без Java-кода.

## 10. Радиосвязь, VTX и failsafe

**Статус:** заготовка. Есть VTX items, link code, станции, synced RSSI и HUD, но

### 10.1. Безопасное управление

- [ ] Заменить глобальный scan всех entity на индекс связей.

- [ ] Arm только по отдельному switch edge при низком throttle.
- [ ] Disarm должен реально работать независимо от keyboard fallback.

### 10.2. Модель сигнала

- [ ] Установленный VTX/receiver должен формировать server-side capabilities.
- [ ] Разделить control link и video link.
- [ ] Рассчитывать distance attenuation, line of sight, материалы блоков,
  воду/землю, высоту и jammer contribution.
- [ ] Использовать block tags для легкого/тяжелого attenuation.
- [ ] Сглаживать RSSI hysteresis/EMA, чтобы HUD не мерцал на границе.
- [ ] Добавить server-side latency/dropout только в разумных пределах без
  ощущения случайного отъема управления.
- [ ] Добавить video noise, `LINK LOW`, `PACKET LOSS`, `JAMMED` и реальные

### 10.3. Failsafe state machine

- [ ] Реализовать состояния `DISARMED`, `ARMED`, `LINK_DEGRADED`, staged

- [ ] Разделить packet age и качество сигнала.

- [ ] Базовая политика - disarm; hover/RTH доступны только с подходящим FC/GPS.
- [ ] Self-destruct разрешать только явно настроенным боевым сборкам.
- [ ] Возвращать управление только после стабильного recovery и безопасной
  процедуры re-entry.
- [ ] Очищать remote session и chunk tickets при logout/death/timeout.

**DoD**

- Любой тип обрыва имеет детерминированный исход и понятен по HUD/звуку.
